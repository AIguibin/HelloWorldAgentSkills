## 前言

本指南定义了一套基于大模型（LLM）的**全自动、端到端、全栈编程**的方法论与操作规范。它将AI作为执行主体，模拟人类开发团队中的多个专业角色，通过标准化的阶段划分、原子任务拆解、自我审查闭环和人机协作边界，实现从用户提供的初步文档到最终可运行代码的全自动生成。

**核心理念**：
- **AI即团队**：AI根据任务需求即时切换角色（需求分析师、架构师、开发工程师、测试工程师等）。
- **文档即代码**：所有需求、设计、测试文档都版本化管理，与源代码同等重要。
- **自闭环质量**：每个任务完成后AI自我审查，即时修复问题，不依赖人工评审。
- **人机协同**：明确人工必须介入的红线环节，确保关键决策的准确性。
- **可追溯可复现**：全过程记录，便于审计和复盘。

本指南适用于全新项目开发、已有项目增量变更、老项目维护等多种场景。遵循本指南，AI可以独立完成从需求理解到代码交付的全流程，人工只需在关键节点进行确认和决策。

## 第一部分：核心理念与角色体系

### 1.1 自主编程与传统开发的区别

| 维度         | 传统人工开发                         | 大模型自主编程                             |
| ------------ | ------------------------------------ | ------------------------------------------ |
| 角色切换     | 需要人员协调、排期                   | AI即时切换角色，无延迟                     |
| 评审审查     | 需要组织会议、等待                   | AI自我审查，即时完成                       |
| 执行时间     | 受工作时间限制                       | 7×24小时连续执行                           |
| 任务拆分     | 需要人工评估、分配                   | AI自动拆分、自动执行                       |
| 文档生成     | 人工编写，耗时较长                   | AI即时生成，格式规范                       |
| 代码审查     | 需要安排审查人员                     | AI自我审查，即时反馈                       |
| 问题响应     | 需要等待人员回复                     | AI即时响应，无需等待                       |
| 知识沉淀     | 依赖人工整理                         | AI自动归档，可追溯                         |

### 1.2 核心原则

- **角色即时切换**：AI根据当前任务自动切换角色，无需等待人员协调。
- **自我审查闭环**：每个任务完成后立即自我审查，发现问题即时修正。
- **7×24连续执行**：AI不受时间限制，可连续不间断执行直至任务完成。
- **文档即代码**：所有文档（需求、设计、测试用例）都视为代码，版本化管理。
- **即时反馈**：遇到疑问立即提出，不猜测、不假设，等待明确答复后继续。
- **可追溯可复现**：所有执行过程都有记录，可随时追溯、随时复现。

### 1.3 角色体系与切换机制

| 角色             | 职责                                           | 输入                     | 输出                     | 切换条件                         |
| ---------------- | ---------------------------------------------- | ------------------------ | ------------------------ | -------------------------------- |
| 文档理解专家     | 阅读输入文档，提取关键信息，识别缺口           | 初步文档                 | 文档理解分析报告         | 用户提供文档后自动切换           |
| 需求分析专家     | 需求分析、拆分、场景穷举、编写需求文档         | 用户意图/确认书          | 需求规格说明书           | 理解确认后切换                   |
| 架构设计专家     | 系统架构设计、数据库设计、接口设计             | 需求文档                 | 概要设计文档             | 需求审查通过后切换               |
| 详细设计专家     | 模块详细设计、伪代码、异常处理设计             | 概要设计文档             | 详细设计文档             | 概要设计审查通过后切换           |
| 开发专家         | 任务拆分、编码规划                             | 详细设计文档             | 任务清单                 | 详细设计审查通过后切换           |
| 高级开发工程师   | 编码实现、单元测试、接口测试                   | 任务清单                 | 源代码+测试代码          | 任务拆分完成后切换               |
| 代码审查员       | 代码审查、质量检查                             | 源代码                   | 审查意见                 | 代码编写完成后切换（自我审查）   |
| 测试工程师       | 测试用例设计、接口测试                         | 接口文档                 | 测试脚本+测试报告        | 接口开发完成后切换               |
| 文档管理员       | 文档归档、版本管理、变更追溯                   | 所有文档                 | 版本化文档库             | 每个阶段完成后切换               |
| 沟通专家         | 生成问题清单、与用户交互                       | 信息缺口清单             | 结构化问题清单           | 需要用户澄清时切换               |
| 技术研究专家     | 查询未知概念、评估技术可行性                   | 未知术语/技术选型        | 术语查询报告/可行性分析  | 遇到未知概念或技术风险时切换     |
| 配置专家         | 生成skill_config.yaml等配置文件                | 用户确认书               | 配置文件                 | 意图确认后切换                   |

## 第三部分：启动阶段 —— 文档理解与意图分析（阶段0）

### 3.1 阶段0概述

阶段0是整个流程的起点，负责理解用户提供的初步文档，分析用户意图，识别信息缺口，通过提问澄清，最终获得用户对AI理解的确认。这一阶段确保后续执行不偏离用户期望，避免执行过程中频繁中断。

**输入**：用户放置在项目根目录 `auto/00-stage-user-input/` 下的初步文档（需求、设计、示例代码等）。  
**输出**：意图确认书、配置文件、标准化需求文档，均存放于 `auto/00-stage-llm-output/` 及其他 `auto/` 子目录。

### 3.2 阶段0执行流程

1. **Step 0.1 文档收集与整理**：扫描输入目录，分类文档，生成文档清单。
2. **Step 0.2 文档阅读与理解**：逐篇阅读，提取关键信息（目标、功能、技术栈、约束）。
3. **Step 0.3 文档完整性分析**：对照标准模板，识别缺失章节和信息，评估完整度。
4. **Step 0.4 用户意图分析**：分析显性/隐性需求，确定优先级。
5. **Step 0.5 技术可行性分析**：评估技术选型，识别外部依赖和风险。
6. **Step 0.6 未知概念识别与查询**：对专业术语进行网络搜索，记录理解。
7. **Step 0.7 生成澄清问题**：基于信息缺口，生成必答/选答问题。
8. **Step 0.8 向用户提问**：结构化展示问题，等待回答。
9. **Step 0.9 迭代澄清**：分析回答，识别新问题，最多3轮。
10. **Step 0.10 生成意图确认书**：汇总确认信息，提交用户最终确认。
11. **Step 0.11 用户确认意图**：用户确认或修改，获得最终确认。
12. **Step 0.12 自动生成配置文件**：生成 `skill_config.yaml`（存放于 `auto/`）和 `user_requirement.md`（存放于 `auto/00-stage-llm-output/` 或技能库的prompt目录）。

### 3.3 阶段0原子执行计划

阶段0被拆分为32个原子任务，每个任务约10-20分钟，确保可执行、可追踪。任务清单如下（所有输出文件均按规范命名并存放于对应目录）：

## 第四部分：需求分析阶段（阶段1-2）

### 4.1 需求分析SOP

**输入**：用户意图确认书、user_requirement.md（初步）  
**输出**：需求规格说明书（定版）

**Step 1 需求理解**
- 分析业务背景，识别核心功能和辅助功能，识别用户角色和使用场景。
- 如有疑问，立即向用户提出。

**Step 2 需求拆分**
- 将大需求拆分为功能模块，再拆分为用户故事（每个1-3天完成）。

**Step 3 场景穷举**
- 对每个用户故事穷举正常、异常、边界、权限、状态场景。

**Step 4 数据字典定义**
- 识别所有数据实体，定义字段（名称、类型、长度、必填、说明），定义实体间关系。

**Step 5 需求文档编写**
- 按照模板编写需求规格说明书（Markdown），包含概述、业务流程、功能需求、数据字典、场景清单。

**Step 6 AI自我审查**
- 对照审查清单检查完整性、准确性、一致性、可测试性，发现问题立即修改。

### 4.2 需求拆分方法

- **MECE原则**：相互独立，完全穷尽。
- **用户故事粒度**：每个故事1-3天完成，有明确的验收标准（Given-When-Then格式）。
- **可测试性**：每个需求必须有明确的输入、输出、预期结果。

### 4.3 场景穷举方法

| 场景类型 | 描述                                         | 示例                                 |
| -------- | -------------------------------------------- | ------------------------------------ |
| 正常场景 | 用户按预期操作，系统正常响应                 | 新增字典类型成功                     |
| 异常场景 | 用户输入错误、系统异常、网络/数据库异常      | 字典类型编码重复                     |
| 边界场景 | 空数据、大量数据、最大值、最小值、零值、超时 | 删除字典类型时存在子项               |
| 权限场景 | 不同角色的操作权限                           | 无权限用户尝试删除                   |
| 状态场景 | 不同状态下的操作限制                         | 已禁用的字典项不能修改               |

### 4.4 AI自我审查机制

AI完成需求文档后立即自我审查，无需人工评审。

**完整性检查清单**：

## 第六部分：编码实现阶段（阶段5-6）

### 6.1 编码前准备

- **理解设计文档**：阅读详细设计，明确实现目标。
- **收集样例代码**：在项目中查找类似实现，分析结构和规范。
- **确认编码规范**：命名规范、代码格式、注释规范、异常处理规范。
- **准备开发环境**：确认代码分支、依赖已导入。

### 6.2 代码生成规范

- **参考样例，保持一致**：保持代码风格、命名规范一致。
- **遵循设计，不偏离**：严格按照详细设计实现，如有问题提出疑问。
- **完整实现，不遗漏**：实现所有功能点，处理所有异常场景，编写完整注释。

**样例代码适配复用规则**：
- **可复用**：通用CRUD、工具方法、设计模式、配置。
- **禁止照搬**：业务逻辑冲突、数据模型差异、存在技术债务、过度设计。

### 6.3 单元测试SOP

- **覆盖率目标**：行覆盖率≥80%，分支覆盖率≥70%，公共方法覆盖率100%。
- **Mock规范**：外部依赖（Mapper、外部服务、缓存、消息队列）必须Mock；不Mock被测类本身、内部逻辑、简单POJO。
- **边界场景测试**：空值、数值边界、长度边界、数量边界。

### 6.4 代码审查SOP

AI完成编码后立即进行自我审查，根据问题级别处理。

**代码审查清单**：
- 命名规范（类大驼峰、方法小驼峰、变量小驼峰、常量大写下划线）
- 代码格式（缩进4空格、行宽≤120、大括号不换行）
- 注释（类有JavaDoc、公共方法有JavaDoc、复杂逻辑有行注释）
- 异常处理（统一异常处理、业务异常使用BusinessException、异常信息友好）
- 日志记录（关键操作记录日志、日志级别正确）
- 单元测试（每个公共方法有单元测试、覆盖所有分支、边界场景）

**问题分级与处理**：

| 级别   | 定义                       | 处理时限 | 是否阻塞后续 |
| ------ | -------------------------- | -------- | ------------ |
| 阻塞   | 功能错误、安全漏洞、性能严重 | 立即修复 | 是           |
| 建议   | 命名不规范、缺少注释、代码重复 | 1天内    | 否           |
| 提示   | 格式问题、代码简化         | 可选     | 否           |

### 6.5 接口测试SOP

- **Step 1 生成测试用例**：根据接口文档生成正常、异常、边界用例。
- **Step 2 生成curl命令**：转换为可执行脚本。
- **Step 3 执行测试**：记录实际响应，对比预期。
- **Step 4 生成测试报告**：汇总结果，分析失败原因。

**测试用例类型**：
- 正常场景：所有必填参数正确，预期成功。
- 异常场景：缺少必填参数、参数格式错误、参数值非法、业务规则冲突，预期错误。
- 边界场景：参数值为空、最大值、最小值，预期根据业务规则返回。

**代码变更与测试用例同步更新规则**：

| 变更类型     | 测试用例更新要求       |
| ------------ | ---------------------- |
| 新增接口     | 必须新增测试用例       |
| 修改接口入参 | 必须更新测试用例       |
| 修改接口出参 | 必须更新测试用例       |
| 修改校验规则 | 必须更新测试用例       |
| 修改业务逻辑 | 必须更新测试用例       |
| 删除接口     | 必须删除测试用例       |
| 重构代码     | 验证现有测试通过       |

### 6.6 技术债务管理

- **识别**：在编码和审查过程中识别技术债务。
- **记录**：使用技术债务清单，包含ID、类型、位置、描述、影响、优先级、状态、创建时间、解决方案。

## 第七部分：变更与维护（增量更新与老项目）

### 7.1 小范围变更增量更新SOP

**变更影响范围分析**：

| 变更类型   | 影响范围                   | 需要更新的上下文             |
| ---------- | -------------------------- | ---------------------------- |
| 新增字段   | 实体类、DTO、接口          | 数据字典、接口契约           |
| 修改字段   | 实体类、校验规则           | 数据字典                     |
| 删除字段   | 实体类、DTO、接口          | 数据字典、接口契约           |
| 修改校验规则 | Service层                  | 业务规则                     |
| 修改业务逻辑 | Service层                  | 业务规则、伪代码             |
| 新增接口   | Controller层               | 接口契约                     |

**增量上下文更新规则**：
- **最小更新原则**：仅更新受影响上下文，保留未受影响部分。
- **版本递增原则**：每次变更增加版本号，记录变更内容。
- **一致性原则**：更新后上下文保持一致，数据字典与代码一致。

**复用 vs 重新生成判定规则**：

| 情况     | 处理方式 | 示例                         |
| -------- | -------- | ---------------------------- |
| 逻辑无变化 | 完全复用 | delete方法逻辑不变           |
| 参数变化 | 修改后复用 | 新增字段，需要处理           |
| 逻辑变化 | 重新生成 | 删除逻辑从提示改为级联       |
| 新增功能 | 新增代码 | 新增导出功能                 |

### 7.2 维护老项目SOP

**与全新项目的区别**：

| 维度       | 全新项目开发         | 老项目维护                 |
| ---------- | -------------------- | -------------------------- |
| 设计起点   | 从零开始设计         | 基于现有设计增量调整       |
| 架构决策   | AI自主设计           | 需对比现有架构，人工决策   |
| 数据库设计 | 全新设计             | 查询现有表，增量变更       |
| 代码复用   | 参考样例             | 直接复用现有代码           |
| 变更范围   | 全量                 | 增量                       |
| 风险评估   | 技术风险             | 兼容性风险+技术风险        |
| 回滚方案   | 无需                 | 必须准备                   |

**执行流程**：
1. **项目现状分析**：读取项目文档，分析结构，识别技术栈，梳理功能模块。
2. **需求变更分析**：理解变更需求，对比现有功能，识别变更点，分析影响范围。
3. **现有架构分析**：分析现有架构，对比差异，输出架构调整建议（需技术总监确认）。
4. **数据库现状分析**：查询现有表，识别需要变更的表，生成数据库变更脚本（ALTER TABLE）。
5. **代码变更分析**：分析现有代码，识别需要变更和可复用的部分，制定变更计划。
6. **增量开发**：优先复用现有代码，仅变更必要部分，保持代码风格一致。
7. **回归测试**：测试变更功能，回归测试未变更功能，验证兼容性。

**增量开发原则**：
- 优先复用
- 最小变更
- 兼容性优先
- 可回滚（每个变更独立回滚，准备回滚脚本）

## 第九部分：多轮生成上下文管理

### 9.1 上下文核心信息范围

- **需求核心规则**：功能目标、业务约束、验收标准
- **架构设计决策**：技术栈选择、分层架构、模块划分
- **数据字典**：所有实体定义、字段约束、表间关系
- **接口契约**：接口路径、请求/响应格式、错误码定义
- **业务规则**：校验规则、计算逻辑、状态流转
- **安全红线**：敏感数据处理规则、权限控制要求、安全约束

### 9.2 上下文版本锚定机制

所有AI生成必须基于定版的前置文档版本。

- **Step 1**：前置文档审查通过并定版，分配版本号。
- **Step 2**：AI记录锚定版本（如“基于需求文档v1.0.0”）。
- **Step 3**：后续生成基于锚定版本，不参考未定版内容。
- **Step 4**：前置文档变更后，重新定版，更新锚定版本，基于新版本重新生成。

### 9.3 上下文偏差校验与修正机制

- **每轮生成后**：自动校验与前置上下文的一致性。
- **阶段切换时**：全面校验，确保前后逻辑一致。
- **人工复核时**：检查一致性，发现偏差及时修正。

### 13.3 核心脚本说明

所有脚本位于技能目录的 `scripts/` 下，执行时需指定工作目录（项目根目录），以便正确读写 `auto/` 下的文件。

#### 00_stage_doc_analyzer.py
- **功能**：阶段0的核心脚本，负责文档理解、意图分析、问题生成、配置生成。
- **命令参数**：
  - `--mode analyze`：启动文档分析
  - `--mode answer --file answers.json`：提交用户回答
  - `--mode confirm --pass`：确认意图

### 15.1 术语表

| 术语             | 解释                                             |
| ---------------- | ------------------------------------------------ |
| SOP              | 标准操作程序（Standard Operating Procedure）     |
| PDCA             | 计划-执行-检查-处理循环                          |
| MECE             | 相互独立，完全穷尽                               |
| 技术债务         | 因快速开发而积累的代码或设计问题，需后续偿还     |
| 原子执行计划     | 不可再分的单个任务，每个任务2-8小时完成          |
| 上下文锚定       | 基于定版文档版本进行后续生成，确保一致性         |
| 意图确认书       | 阶段0产出的用户与AI共识文档，指导后续执行        |

### 15.2 常见问题

**Q1: 阶段0需要多长时间？**  
取决于文档数量和复杂度，通常30分钟-2小时（AI分析10-30分钟，用户回答20-90分钟）。

**Q2: 如果文档不完整怎么办？**  
AI会识别信息缺口，生成问题清单向您提问。您可以选择回答或接受默认值。

**Q3: 可以不执行阶段0吗？**  
可以。如果已有完整的 `skill_config.yaml` 和 `user_requirement.md`，使用 `--skip-stage0` 跳过。

**Q4: 阶段0生成的配置可以修改吗？**  
可以。您可以在执行前手动修改 `auto/skill_config.yaml`，也可在执行过程中通过人工复核节点调整。

**Q5: 如果AI理解错了怎么办？**  
在意图确认书环节，您可以指出理解错误的地方，AI会重新分析并修正。

**Q6: 项目代码生成在什么位置？**  
默认在项目根目录下的 `src/` 中，技能会根据 `skill_config.yaml` 中配置的技术栈生成对应的项目结构（如 Java Maven 项目的 `src/main/java`，Node.js 项目的 `src/` 等）。同时会生成相应的构建配置文件（如 `pom.xml`、`package.json`）。

**Q7: 支持哪些编程语言？**  
本指南不限定语言，技能通过 `skill_config.yaml` 中的 `tech_stack` 配置来适配不同语言的项目结构。示例中给出了 Java（Maven）的结构，同样适用于 Node.js（package.json）、Python（requirements.txt）等项目。
