# 湖北农信新信贷数据库表分区策略设计文档 Spec

## Why
基于原始人工标注分区清单（93张需分区表，G列="是"），结合信贷业务全生命周期知识、老信贷生产环境数据量基准、GoldenDB 分布式数据库特性，按照《新信贷业务数据库表分区设计文档编写指南》的7章标准大纲，输出一份面向业务与技术融合的专业表分区策略设计文档。

## What Changes
- 新增：产出《湖北农信新一代信贷管理系统数据库表分区策略设计文档》（.docx 格式）
- 严格遵循编写指南的7章结构：业务与数据特征分析 → 分区目标与设计原则 → 核心表分区方案设计 → 分区索引与约束策略 → 分区管理与运维方案 → 性能与扩展性验证 → 风险与回滚预案
- 技术选型：GoldenDB 分布式数据库（MySQL 兼容），需考虑其分布式特性（计算节点 + 数据节点 + 全局事务管理器）
- **以原始人工标注清单（`湖北农信数据库分区表清单.xlsx`）为权威数据源**，93张G列="是"的表为分区方案基础，所有人工标注的分区键和分区数均视为正常设计

## Impact
- 新增文件：`FF--湖北农信新信贷数据库设计策略\湖北农信新信贷数据库表分区策略设计文档.docx`
- 参考文件：
  - `AE-编写指南\新信贷业务数据库表分区设计文档编写指南.md`（文档结构遵循标准）
  - `DD-湖北农信基础配置检核\湖北农信数据库分区表清单.xlsx`（**原始人工标注清单，权威数据源**）
  - `AA-数据量\老信贷生产环境迁移表数据量.xlsx`（生产数据量基准）
  - `CC-新信贷基础知识\*.txt`（信贷业务知识库，8个章节）
  - `EE-湖北农信新信贷数据库设计文档\*.xlsx`（23个设计文档，表结构设计，按需查阅）
  - `BB-汇总文件\`（汇总结果文件目录）

## 文档输出规范

### 格式要求
- 输出格式：.docx（Word 文档）
- 语言：中文
- 风格：专业、严谨，业务视角与技术视角深度融合
- 必须包含：目录、页眉页脚、表格、分区策略 DDL 示例

### 内容要求（7章）

#### 第1章：业务与数据特征分析
- 梳理湖北农信新信贷系统的核心业务实体（客户、合同、借据、还款计划、还款明细、押品、档案、征信查询等）
- 从老信贷生产环境数据量 Excel 提取关键数据量级，整理 TOP 30 大表清单
- 说明各实体间的数量关系（1客户→N合同→N借据→N还款计划→N还款明细）
- 区分联机交易、批量/报表、监管报送三类访问模式
- 结合《个人信息保护法》《银行业金融机构数据治理指引》明确数据保留期限

#### 第2章：分区目标与设计原则
- 明确目标：大表（>1000万行）性能不退化、按月滚动分区秒级归档、避免联机交易跨分区扫描
- GoldenDB 特性说明：分布式数据库的分区与分片关系、全局索引限制、分区键必须纳入主键
- 四大原则：业务内聚、时间窗口对齐、运维可操作、冷热分离
- 分区键选择原则：以人工标注的原始分区键为准，分析每种分区键选择背后的业务逻辑

#### 第3章：核心表分区方案设计（重点章节）
- 对93张需分区表，按业务模块分组（合同管理/客户中心/授信管理/放还款/档案管理/用信管理/系统管理/营销管理/评级管理/贷后管理/风险分类/额度管理/征信）
- 每个模块组按"业务驱动→分区键选择→分区粒度→分区策略"逻辑链展开
- 分析人工标注的分区键选择的业务合理性（如：TENANT_ID 按法人行隔离、CTRT_NO 按合同编号分布、CUST_NO 按客户编号分布、BUS_NO 按业务流水号分布、TSK_NO 按任务编号分布、CREATE_TIME 按时间分区）
- 给出核心表的 DDL 示例（GoldenDB MySQL 8.0 兼容语法）

#### 第4章：分区索引与约束策略
- 本地索引 vs 全局索引的选择策略
- GoldenDB 下主键、唯一索引必须包含分区键的设计约束
- 统计类批量扫描走本地索引，单笔查询利用日期字段
- 外键约束的处理（应用层保证一致性）

#### 第5章：分区管理与运维方案
- 自动化分区创建/删除/归档脚本框架
- 归档策略：结清贷款分区交换 → 历史表 → 离线文件
- 监控指标：分区倾斜度、跨分区SQL、全局索引失效
- 银行业务日历关联：年终决算、结息日等特殊时点的维护窗口

#### 第6章：性能与扩展性验证
- 基于生产数据量进行模拟验证
- 对比分区前后的执行计划和响应时间
- 分区裁剪失败的场景预警（如 WHERE 条件使用函数导致裁剪失效）

#### 第7章：风险与回滚预案
- 技术风险：GoldenDB 跨分区事务、分区键字段更新导致行迁移
- 业务风险：分区漏建导致交易中断
- 回滚方案：非分区表映射视图 + 快速反向脚本

## ADDED Requirements

### Requirement 1: 文档结构完整性
系统 SHALL 输出包含完整7章的 .docx 文档，每章有明确的标题、正文、表格、DDL 示例。

#### Scenario: 文档生成成功
- **WHEN** 所有输入数据准备就绪
- **THEN** 生成包含目录、7章完整内容、附录的 .docx 文件

### Requirement 2: 以原始人工标注清单为权威数据源
系统 SHALL 以 `湖北农信数据库分区表清单.xlsx` 中 G列="是" 的93张表作为分区方案基础：
- 完整保留原始人工标注的分区键、分区数、责任人信息
- 所有人工标注的分区键（包括 TENANT_ID、CTRT_NO、CUST_NO、BUS_NO、TSK_NO、GTCR_CUST_NO、CREATE_TIME 等）均视为正常设计
- 文档中分析每种分区键选择背后的业务逻辑，而非评判其优劣

#### Scenario: 分区表引用正确
- **WHEN** 文档引用分区表信息
- **THEN** 分区键直接使用原始清单中的值，保持与人工标注一致

### Requirement 3: 生产数据量引用
系统 SHALL 从 `老信贷生产环境迁移表数据量.xlsx` 提取 TOP 30 大表的数据量，用于第1章的数据特征分析。

#### Scenario: 数据量引用正确
- **WHEN** 文档中提到某张表的数据量
- **THEN** 数据量来源于生产环境迁移表，标注"当前存量"并与5-8年预估量区分

### Requirement 4: GoldenDB 技术适配
系统 SHALL 在文档中体现 GoldenDB 分布式数据库的特定约束：
- 分区键必须纳入主键和唯一索引
- 不支持全局唯一索引（需设计规避方案）
- 分布式事务的跨分区一致性考量
- DDL 示例使用 MySQL 8.0 兼容语法

#### Scenario: GoldenDB DDL 语法正确
- **WHEN** 文档包含 DDL 示例
- **THEN** 语法符合 MySQL 8.0 分区规范，且包含 GoldenDB 特有的分布式表定义

### Requirement 5: 信贷业务语义融合
系统 SHALL 在文档中融入信贷业务知识，用业务语言解释技术决策：
- 例如："之所以采用放款日期而非系统日期，是为了确保即使出现冲正，同一笔业务的所有操作都落在同一分区"
- 引用信贷全生命周期流程（贷前→贷中→贷后）说明数据产生时机
- 结合湖北农信业务特点（日均放款量、客户规模、产品结构）进行个性化分析

#### Scenario: 业务语言解释技术决策
- **WHEN** 文档做出分区键选择等技术决策
- **THEN** 附带业务语义解释，而非纯技术理由

### Requirement 6: 分区策略总结表
系统 SHALL 在第3章末尾提供一张完整的93张分区表策略总结表，包含：
- 序号、所属模块、表英文名、表中文名、责任人、分区键、分区数、分区策略描述

#### Scenario: 总结表完整
- **WHEN** 文档第3章完成
- **THEN** 总结表覆盖全部93张表，无遗漏
