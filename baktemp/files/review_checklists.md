# 各阶段自我审查清单

> 使用方法：每个阶段完成后，切换为"代码审查员"角色，对照对应清单逐项检查。
> 所有项目必须通过（✅）才能进入下一阶段。发现问题立即修正后重新检查。

---

## 审查清单1：需求分析审查

### 完整性
- [ ] 文档结构完整（概述/业务流程/功能需求/数据字典/场景清单/非功能需求）
- [ ] 所有功能点已描述，无遗漏
- [ ] 每个用户故事都有 Given-When-Then 验收标准
- [ ] 数据字典定义了所有实体的所有字段（含类型/长度/必填/说明）
- [ ] 场景清单覆盖：正常场景、异常场景、边界场景、权限场景、状态场景

### 准确性
- [ ] 业务描述准确，无歧义
- [ ] 数据字典字段类型、长度、必填设置正确
- [ ] 验收标准可量化、可测试（有明确输入/操作/预期结果）

### 一致性
- [ ] 术语使用统一（同一概念只有一个名称）
- [ ] 前后描述一致，无矛盾
- [ ] 数据字典与功能描述一致

### 可测试性
- [ ] 每个验收标准都有具体的输入、操作、预期结果
- [ ] 无"合法数据"、"合理范围"等模糊描述

---

## 审查清单2：概要设计审查

### 架构设计
- [ ] 分层设计合理（Controller/Service/Mapper 职责清晰，不互相越界）
- [ ] 模块划分合理，职责单一
- [ ] 模块间依赖方向正确（高层依赖低层，不反向依赖）
- [ ] 技术选型符合 `skill_config.yaml` 中配置的技术栈

### 数据库设计
- [ ] 表结构与数据字典完全对应（字段名/类型/长度一致）
- [ ] 每张表包含通用字段（id/create_time/update_time/is_deleted/create_by/update_by）
- [ ] 字段类型和长度合理（不无脑 varchar(255)，根据实际业务设计）
- [ ] 主键设计合理（bigint自增 或 雪花ID）
- [ ] 外键关联字段已建索引
- [ ] 频繁查询字段已建索引
- [ ] 所有表和字段有注释（COMMENT）
- [ ] 建表SQL可直接执行（无语法错误，在目标数据库版本验证通过）

### 接口设计
- [ ] 路径符合 RESTful 规范（名词复数，无动词，如 `/api/dict-types`）
- [ ] HTTP方法使用正确（GET查/POST增/PUT全量改/PATCH部分改/DELETE删）
- [ ] 请求参数定义完整（类型/是否必填/校验规则/说明）
- [ ] 响应使用统一格式 `{code, message, data}`
- [ ] 错误码有完整定义（code含义/触发条件/响应示例）
- [ ] 分页接口返回 total（不能只返回当页数据）

---

## 审查清单3：详细设计审查

- [ ] 每个核心方法都有伪代码
- [ ] 伪代码覆盖所有业务分支（正常 + 所有异常）
- [ ] 参数校验在伪代码中有体现（null/格式/业务规则）
- [ ] 事务边界在伪代码中明确标注（哪些操作在同一事务内）
- [ ] 每种异常都有明确的错误码和响应描述
- [ ] 伪代码不依赖特定编程语言语法，任何人都能理解

## 审查清单4：代码审查（每个任务完成后必查）

### 🔴 P0 阻塞问题（发现即停止，必须修复后才能继续）

- [ ] **无SQL注入风险**（使用参数化查询，禁止字符串拼接构造SQL）
- [ ] **无高风险NPE**（所有可能为null的对象在使用前已判断）
- [ ] **无敏感信息泄露**（密码/Token/私钥未出现在日志或API响应中）
- [ ] **事务完整**（多步写操作在同一 @Transactional 方法内）
- [ ] **测试覆盖率达标**（行≥80%，分支≥70%，方法=100%）

### 🟡 代码规范（修复后继续）

**命名规范**
- [ ] 类名使用 UpperCamelCase（如 `DictTypeServiceImpl`）
- [ ] 方法名/变量名使用 lowerCamelCase（如 `dictTypeCode`）
- [ ] 常量使用 UPPER_CASE_WITH_UNDERSCORES
- [ ] 无无意义命名（a, b, temp, obj, data1...）
- [ ] 无拼音命名（如 `ziDianLeiXing`）

**代码质量**
- [ ] 无魔法数字（使用常量或枚举代替字面值）
- [ ] 无空 catch 块
- [ ] 无重复代码（DRY原则，可提取公共方法）
- [ ] 无在循环内执行数据库查询（N+1问题）
- [ ] 无未使用的import和变量

**注释规范**
- [ ] 所有 public 方法有 JavaDoc 注释（@param/@return/@throws）
- [ ] 复杂业务逻辑有行内注释（解释"为什么"，不是"是什么"）
- [ ] 类头有 JavaDoc 注明职责和对应设计文档

**日志规范**
- [ ] 使用 @Slf4j，不使用 System.out.println
- [ ] 关键操作有 INFO 级别日志（包含关键上下文如ID/操作类型）
- [ ] 异常有 ERROR 级别日志（必须包含异常对象本身）
- [ ] 日志信息中无密码、Token 等敏感信息

**Spring 规范**
- [ ] Controller 层不含业务逻辑（只做：参数接收/校验/调Service/返回结果）
- [ ] Service 层涉及写操作已加 `@Transactional`
- [ ] 使用构造器注入（或 @RequiredArgsConstructor），不使用字段注入
- [ ] 请求对象有 `@Valid` 注解，字段有 Bean Validation 注解

**MyBatis-Plus 规范**
- [ ] 实体类有 `@TableName` 和 `@TableId`
- [ ] 逻辑删除字段有 `@TableLogic`
- [ ] 批量操作使用 `saveBatch`（不循环单条insert）
- [ ] 查询指定必要字段（避免 `SELECT *`）

## 审查清单5：单元测试审查

- [ ] 每个 public 方法至少有1个正常场景测试
- [ ] 覆盖了所有异常场景（每种业务异常 + 空指针边界）
- [ ] 覆盖了边界场景（null/空字符串/最大值/最小值）
- [ ] 所有外部依赖（Mapper/外部Service/Redis）已 Mock
- [ ] 未 Mock 被测类本身的内部逻辑
- [ ] 测试方法命名规范：`方法名_场景描述_预期结果`
- [ ] 测试可独立运行，不依赖外部环境（数据库/网络/时间）
- [ ] 测试运行全部通过（无红色失败）

---

## 审查清单6：接口测试审查

- [ ] 每个接口端点有 curl 测试脚本
- [ ] 正常场景通过，响应 code=0
- [ ] 缺少必填参数场景通过，响应 code=400
- [ ] 参数格式错误场景通过，响应 code=400
- [ ] 业务规则冲突场景通过，响应业务错误码
- [ ] 测试脚本可在终端直接执行（无语法错误）

## PDCA循环检查清单（每个原子任务执行时）
