# Part A：维护老项目SOP（Section 12）

## 老项目 vs 全新项目的核心区别

| 维度 | 全新项目 | 老项目维护 |
|-----|---------|----------|
| 代码基础 | 从零开始 | 在现有代码上修改 |
| 需求形式 | 完整需求文档 | 变更需求（增量） |
| 数据库 | 全新建表 | ALTER TABLE变更 |
| 测试重点 | 功能测试 | 回归测试为主 |
| 代码风格 | 按规范新建 | **必须匹配现有代码风格** |
| 核心原则 | 构建 | **最小变更，优先复用** |

## 老项目维护执行入口

当用户说"老项目新增功能"、"修改现有功能"、"项目维护"时，从以下流程开始：

```bash
# 扫描项目现状
python scripts/ai_auto_dev.py --phase legacy-analysis
```

## 老项目维护执行流程（7阶段）

### 阶段L1：项目现状分析

**角色**：代码理解专家 → 项目分析专家（以架构设计专家角色执行）

**执行内容**：
1. 读取现有项目文档（需求文档、设计文档、README等，如有）
2. 分析项目结构（目录结构、模块划分）
3. 识别技术栈（框架版本、依赖库）
4. 阅读现有代码，提取代码风格（命名规范、注释规范、代码结构）
5. 梳理现有功能模块

**交付物**：`02_exec_plans/legacy/L1-项目现状分析报告.md`

### 阶段L2：需求变更分析

**角色**：需求分析专家

**执行内容**：
1. 理解用户变更需求（新增/修改/删除的功能）
2. 对比现有功能，识别变更点
3. 分析变更影响范围（哪些模块受影响）
4. 输出变更需求文档（增量形式，不是全量重写）

**交付物**：`02_exec_plans/legacy/L2-变更需求规格说明书.md`

**格式**：变更需求使用增量描述：
```markdown
## 变更点 1: {功能名称}

**变更类型**：新增 / 修改 / 删除

**现有功能**：{现有功能的描述}

**变更后功能**：{变更后的描述}

**影响范围**：
- 影响模块：{模块列表}
- 影响接口：{接口列表}
- 影响数据库表：{表名列表}
```

### 阶段L3：现有架构分析

**角色**：架构设计专家（以架构分析专家角色）

**执行内容**：
1. 分析现有架构设计
2. 识别需要实现的架构目标（变更后的目标）
3. 对比现有架构与目标架构的差异
4. 输出架构调整建议

**交付物**：`02_exec_plans/legacy/L3-架构对比分析报告.md`

> ⚠️ 此交付物需要**技术总监确认**（红线2：技术架构决策）

### 阶段L4：数据库变更分析

**角色**：数据库分析专家（以架构设计专家角色）

**执行内容**：
1. 查询现有数据库表清单
2. 读取历史表结构
3. 对比变更需求，识别需要新增/修改/删除的表和字段
4. 输出数据库变更脚本（`ALTER TABLE`，不是重新建表）

**交付物**：`02_exec_plans/legacy/L4-数据库变更脚本.sql`

```sql
-- 变更脚本示例
-- 变更说明：为 user 表新增 phone_verified 字段
-- 执行时间：XXXX-XX-XX
-- 回滚脚本：ALTER TABLE user DROP COLUMN phone_verified;

ALTER TABLE user ADD COLUMN phone_verified tinyint(1) NOT NULL DEFAULT 0 COMMENT '手机号是否已验证 0-未验证 1-已验证' AFTER phone;
CREATE INDEX idx_phone_verified ON user(phone_verified);
```

### 阶段L5：代码变更分析

**角色**：代码分析专家（以高级开发工程师角色）

**执行内容**：
1. 分析现有代码结构
2. 识别需要变更的代码文件（精确到类和方法）
3. 识别可以复用的代码（不变更的部分）
4. 制定代码变更计划（增量，不是全量重写）

**交付物**：`02_exec_plans/legacy/L5-代码变更计划.md`

格式：
```markdown
| 变更类型 | 文件路径 | 类名 | 方法名 | 变更说明 |
|---------|---------|-----|-------|---------|
| 新增 | .../service/UserService.java | UserService | verifyPhone() | 新增手机号验证方法 |
| 修改 | .../controller/UserController.java | UserController | register() | 注册逻辑增加验证步骤 |
| 不变 | .../mapper/UserMapper.java | UserMapper | 全部 | 无需修改 |
```

### 阶段L6：增量开发

**角色**：高级开发工程师 ↔ 代码审查员

**增量开发核心原则**（严格遵守）：
- **优先复用**：复用现有代码结构、设计模式、代码风格
- **最小变更**：仅变更必要的部分，避免大面积重构
- **兼容性优先**：保持接口兼容性，保持数据兼容性，提供适配层（如需要）
- **可回滚**：每个变更都可独立回滚，记录变更前状态，准备回滚脚本
- **风格一致**：新增代码与现有代码风格完全一致（参考L1阶段的代码风格分析）

**PDCA循环**（同全新项目，但特别注意）：
- Plan 阶段：必须先读取要修改的现有代码，理解其逻辑
- Do 阶段：优先复用现有模式，仅修改必要部分
- Check 阶段：额外检查兼容性（接口/数据/行为）

### 阶段L7：回归测试

**角色**：测试工程师

**执行内容**：
1. 测试变更功能（新增/修改的功能点）
2. **回归测试**未变更功能（确保没有引入bug）
3. 验证接口兼容性（老客户端是否还能正常工作）
4. 生成测试报告

**交付物**：`03_delivery/legacy_test_report.md`

**老项目维护检查清单**：
- [ ] 是否分析了项目现状？
- [ ] 是否精确识别了变更点？
- [ ] 是否分析了变更影响范围？
- [ ] 数据库变更是否使用 ALTER TABLE（而不是重建）？
- [ ] 是否优先复用了现有代码？
- [ ] 新增代码的代码风格是否与现有代码一致？
- [ ] 是否保持了接口兼容性？
- [ ] 是否准备了回滚脚本？
- [ ] 是否进行了回归测试？

# Part B：小范围变更增量更新SOP（Section 11）

适用场景：已在执行中的项目（exec_index.yaml存在），需要对小范围内容进行变更。

## 变更影响范围分析

| 变更类型 | 影响范围 | 处理策略 |
|---------|---------|---------|
| 需求细节修改 | 当前模块的需求/设计/代码 | 增量更新，标记受影响任务为PENDING |
| 数据库字段新增 | Entity / Mapper / 相关业务逻辑 | 定向修改，不影响其他模块 |
| 接口参数调整 | Controller / DTO / 调用方 | 追加字段（向后兼容），更新接口文档 |
| 业务规则修改 | Service层 + 单元测试 | 修改对应方法，更新测试 |
| 代码重构（不改功能） | 涉及文件 | 纯代码变更，确保测试仍然通过 |

## 增量上下文更新规则

**三条核心原则**：
1. **最小更新**：仅更新受影响的上下文，保留未受影响的上下文，避免全量重写
2. **版本递增**：每次变更增加版本号，记录变更内容，可追溯历史（v1.0.0 → v1.0.1）
3. **一致性**：更新后保持一致，数据字典与代码一致，接口契约与实现一致

## 增量变更执行步骤

```
Step 1: 评估变更影响范围（对照上方表格）

Step 2: 更新受影响文档（版本号递增）
  - 需求文档：v1.0.0 → v1.0.1，追加变更说明
  - 设计文档：相应章节更新
  - 数据字典：更新字段定义

Step 3: 在 exec_index.yaml 中标记受影响的任务
  - 将受影响的已完成任务（DONE）标记为 PENDING（需要重做）
  - 新增必要的新任务（追加到任务列表）

Step 4: 更新 01_context_core/current_context.md 中的锚定版本

Step 5: 按正常PDCA循环执行受影响的任务
```

## 代码复用 vs 重新生成判定

| 条件 | 判定 | 说明 |
|-----|------|-----|
| 改动 < 30% 代码量 | ✅ 复用 + 局部修改 | 保留现有代码，仅修改变更部分 |
| 改动 30-60% 代码量 | ⚠️ 部分复用 | 复用结构，重写业务逻辑 |
| 改动 > 60% 代码量 | ❌ 重新生成 | 此时重新生成更高效 |
| 原代码有P0债务 | ❌ 重新生成 | 不复制有问题的代码 |
| 业务规则冲突 | ❌ 重新生成 | 业务逻辑不同，不能照搬 |

```markdown
**变更原因**：{用户说明}

### 影响范围
- 受影响文档：{文档名} v{旧版本} → v{新版本}
- 受影响任务：{任务ID列表}（已重置为PENDING）
- 新增任务：{新任务ID列表}

### 变更内容摘要
{简要说明变更内容}

### 执行状态
- [x] 文档已更新
- [x] exec_index.yaml 已更新
- [ ] 代码变更已完成
- [ ] 测试已通过
```
